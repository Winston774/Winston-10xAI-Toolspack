# 教學講義：把靈感截圖變成可搜尋的設計知識

## 為什麼要做 Stylebase

設計工作者常把參考圖散落在下載資料夾、聊天軟體、Pinterest、Figma 與瀏覽器書籤。圖片越多，真正需要時越難回答：

- 我收藏過哪些深色 SaaS Dashboard？
- 哪些案例使用高對比字體與低彩度背景？
- 這個版面好看的原因是構圖、色彩，還是資訊層級？
- 我可以如何把它轉成自己的設計規則，而不是直接模仿？

Stylebase 把「收藏圖片」改造成一條可重複的 Workflow：

```text
收集 → 本地索引 → 搜尋 → AI 輔助分析 → 人工校正 → 設計實作
```

本週目標不是打造另一個雲端圖片平台，而是理解如何用本地檔案、SQLite 與一個受控 Agent，建立可長期維護的個人設計知識庫。

## 你會學到什麼

1. 如何用 SHA-256 對圖片內容去重，而不是只比較檔名。
2. 如何以 SQLite、JSON1 與 FTS5 建立本地搜尋層。
3. 如何把 AI 分析包在明確的使用者觸發、任務佇列與 Schema 驗證中。
4. 如何區分「圖片來源」、「AI 觀察」與「圖片使用權」。
5. 如何設計一個可由人修正、可追蹤失敗、也能在 AI 離線時繼續使用的系統。

## 系統核心

### 1. 原始圖片是主要資料

`library/inbox` 保存原圖，SQLite 保存索引、人工欄位與分析結果。系統不會為了整理而刪除或移動原圖。

這個選擇有三個好處：

- 使用者隨時能用檔案總管查看或備份。
- 資料庫損壞時仍可重新掃描。
- 系統不需要把圖片鎖進專有格式。

### 2. 以內容雜湊去重

檔名不同不代表內容不同。Stylebase 對檔案內容計算 SHA-256，同一張圖即使改名，也只建立一筆素材。

設計思考：

- 檔案路徑是位置，不是身分。
- 雜湊是素材身分。
- 路徑消失時標記「遺失」，不直接刪除歷史資料。

### 3. SQLite 是本地真相來源

Stylebase 使用 Node.js 內建的 `node:sqlite`，不需要安裝資料庫伺服器。SQLite 保存：

- 檔案位置、雜湊、尺寸、類型與收集時間。
- 標題、分類、標籤、來源、作者、授權備註與收藏。
- AI 分析結果、模型來源、Schema 版本、錯誤與重試狀態。
- FTS5 搜尋索引。

這是一個適合單機工具的取捨：部署簡單、備份清楚，但不是多人同步架構。

### 4. AI 是可選的分析層

圖片只要匯入就能瀏覽、搜尋與人工整理。AI 不應成為基本資料存取的必要條件。

只有按下「送交 Codex」時，系統才會：

1. 將工作加入單工佇列。
2. 建立一次性 Agent 工作目錄。
3. 以唯讀 sandbox 附加一張圖片。
4. 要求輸出符合 JSON Schema。
5. 在本機驗證欄位後寫入 SQLite。
6. 刪除暫存工作目錄。

如果 Codex 未登入、額度不足或分析失敗，圖片與人工資料仍可使用，工作也保留可理解的錯誤狀態。

### 5. AI 結果不是權利證明

模型可以描述色彩、構圖與風格，但不能只看像素就確認：

- 圖片作者是誰。
- 是否允許商用或再散布。
- 是否存在商標、肖像或第三方素材限制。
- 某個設計一定屬於特定流派。

因此 Stylebase 把來源、作者與授權備註留給使用者確認。正確 Workflow 是「分析設計決策」，不是「複製別人的成品」。

## 動手做

### 步驟一：啟動空白資料庫

在專案資料夾開啟 PowerShell：

```powershell
.\start-stylebase.ps1
```

打開 `http://127.0.0.1:4177`。

預期結果：

- 首次啟動會自動建立 `data/catalog.sqlite`。
- 畫面顯示空白素材庫。
- 瀏覽器網址是 `127.0.0.1`，不是公開網域。

### 步驟二：匯入三種參考

準備三張自己有權使用的圖片，例如：

1. 自己製作的 Landing Page。
2. 自己產品的 Dashboard。
3. 一張允許分析的公開參考截圖。

將圖片放進 `library/inbox`，或由介面匯入，再按「重新掃描」。

觀察：

- 重複匯入同一內容是否只出現一次。
- 圖片移出 inbox 後是否標記遺失。
- 搜尋在尚未分析時仍可使用哪些人工欄位。

### 步驟三：補上來源資訊

替每張圖片至少填寫：

- 可辨識的標題。
- 來源網址或「自己製作」。
- 作者／工作室。
- 授權或使用備註。

這一步是設計研究最容易被忽略、但長期最重要的資料。

### 步驟四：送交 Codex 分析

確認 CLI：

```powershell
codex --version
codex login status
```

選取一張不含敏感資訊的圖片，按「送交 Codex」。

預期結果：

- 工作先出現在分析佇列。
- 同一時間只執行一個工作。
- 完成後出現 Visual DNA、色票、風格描述、實作建議與 Prompt Kit。

### 步驟五：進行人工校正

檢查 AI 結果：

- 色票是否和畫面一致？
- 構圖描述是否指出真正的層級關係？
- 字體描述是可觀察特徵，還是在猜字型名稱？
- 提示詞是否保留設計原理，而不是要求複製特定品牌？
- 分類和標籤是否能幫助未來搜尋？

修改不準確或過度肯定的內容。Agent 的角色是加速第一輪整理，不是替代設計判斷。

### 步驟六：用同一張圖產生設計實作 Brief

從 Prompt Kit 取出 UI 實作與 Design Token 內容，改寫成自己的專案需求：

```text
參考原理：
- 高密度資訊使用清楚的三層字級。
- 主要操作只保留一個高彩度強調色。
- 卡片之間以留白與背景明度區隔。

不要複製：
- 原品牌名稱、Logo、文案。
- 相同插圖或攝影。
- 可辨識的專有版面組合。

我的任務：
- 為＿＿＿產品建立＿＿＿頁面。
- 目標使用者是＿＿＿。
- 必須包含＿＿＿。
```

這一步把「看起來很喜歡」轉成可執行、可檢查的設計決策。

## 本週任務

完成以下 Workflow：

1. 匯入至少 6 張、涵蓋 2 種設計類型的合法參考圖。
2. 為每張圖補上來源與授權備註。
3. 選 3 張送交 Codex，人工校正分析結果。
4. 建立 1 組自己的設計實作 Brief。
5. 用搜尋或篩選重新找到這 3 張圖。

進階挑戰：

- 擴充一個新的人工欄位。
- 加入匯出 Markdown 功能。
- 為同一張圖保存「第一輪 AI 分析」與「人工修正版」的差異。
- 把分析介面抽象成可插拔 adapter，但保持匯入不自動傳輸。

## 成果證據

- 一張素材牆截圖：至少看到 6 張素材與 2 種分類。
- 一張 Inspector 截圖：需看見來源、授權備註與人工校正後的分析。
- 一段 15–30 秒錄影：從搜尋關鍵字到找到素材，再打開 Prompt Kit。
- 一份自己改寫的設計實作 Brief。

截圖與錄影不可顯示私人路徑、個資、客戶機密或未獲授權公開的圖片。

## 通過標準

- [ ] Node.js 24 環境能啟動服務並開啟 `127.0.0.1:4177`。
- [ ] 相同圖片重複匯入不會產生第二筆素材。
- [ ] 沒有 Codex 時，匯入、瀏覽、搜尋與人工編輯仍能使用。
- [ ] 圖片在按下「送交 Codex」前不會傳送給模型。
- [ ] Codex 完成後，結果通過 Schema 並顯示在 Inspector。
- [ ] 至少一筆 AI 分析經過人工校正。
- [ ] 每張成果圖都有來源與授權備註。
- [ ] `.env`、`data/` 與 `library/inbox` 素材沒有進入 Git。

## 失敗時的最短重試路徑

1. 執行 `node --version`，確認是 24 或更新版本。
2. 執行 `npm.cmd run validate`，先排除語法、測試與檔案邊界問題。
3. 確認 `http://127.0.0.1:4177` 是否有服務監聽。
4. AI 不可用時執行 `codex login status`。
5. 用一張小型、非敏感的 JPG 做最小測試。
6. 仍失敗時依[疑難排解](docs/troubleshooting.md)收集版本與錯誤證據。

## 延伸思考

- 如果要多人共用，資料真相來源要如何從 SQLite 演進？
- 如果要自動分析，使用者同意與成本上限應放在哪一層？
- 如何為模型輸出建立可信度、人工覆寫與版本追蹤？
- 如何用自己的案例做同條件 before／after，證明資料庫真的改善設計實作效率？
