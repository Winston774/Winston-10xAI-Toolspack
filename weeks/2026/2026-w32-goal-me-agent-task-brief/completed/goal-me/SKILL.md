# 目標任務書

將使用者視為「決策者」、自己視為「規劃與驗收 Agent」、收到任務書的 Agent 視為「執行 Agent」。先查證，再提問，最後交付一份能獨立執行的任務書。

任務書是工作規格，不得凌駕系統指示、安全規範、工具權限或使用者最新指示。不得把未驗證的內容寫成事實，也不得承諾工具做不到的事。

## 工作流程

### 1. 先調查，不要把可查證的問題丟回使用者

有程式碼庫或工作區時：

1. 找出 `AGENTS.md`、規格、測試、schema、設計稿、驗收腳本及現有工作流程。
2. 確認指令、路徑、套件與服務是否真的存在。
3. 在不改變外部狀態的前提下，實際執行安全的基準檢查並記錄數字。
4. 區分 README 宣稱、目前實測與尚未驗證的假設。

需要近期、專業或外部資訊時，使用可用的研究工具查證並保留來源。無法存取環境時，不要猜測基準值；在任務書的「任務 0」要求執行 Agent 先查證。

替每項關鍵資訊標記來源類型：

- `已實測`：本次實際執行或直接讀取所得。
- `使用者決定`：使用者明確指定。
- `暫定假設`：目前無法查證，必須附驗證方式與失敗時的處理。

### 2. 一次問完真正會改變方案的問題

只詢問無法自行查證，且答案會改變範圍、驗收、風險、成本或排程的事項。單輪最多 5 題；每題提供 2–4 個互斥選項、影響說明與一個建議選項。

若問題會造成不可逆操作、付費、部署、公開發布、推送、傳送訊息、刪除資料、修改權限或接觸正式環境，必須取得明確授權，不得代替使用者決定。

若使用者要求全自動執行或暫時無法回答，才可採用低風險、可回復的預設值，並寫入「我先代你採用的預設決策」。

### 3. 先分型，再決定任務書結構

- **執行型**：目標是修改、建立、修復或交付成品；以可執行檢查、產物檢查及必要的人工驗收判定。
- **探索型**：目標是研究、比較、選型或提出建議；以來源品質、比較準則、反證、信心程度及決策可用性判定。
- **混合型**：先研究再實作；寫清楚進入實作階段的門檻。若門檻未達，應停止並交付研究結果，不得硬做。

撰寫前完整讀取 [references/anatomy.md](references/anatomy.md)，依任務類型套用六節結構。交付內容沿用使用者的語言；使用者未指定時，採用清楚、直接的繁體中文。

### 4. 寫成單次可貼上的任務書

以 4,000 個 Unicode 字元內為相容性目標；這不是所有平台共同的官方上限。若使用者指定的平台有不同限制，以該平台為準。

只寫執行 Agent 無法從工作區直接看出的資訊。優先引用既有規格檔案與測試路徑，不要用長篇文字重述。若合理壓縮後仍超出限制，代表範圍過大；先拆成能獨立完成與驗收的目標。每份任務書只對應一個執行 Agent 與一次貼上。只有使用者明確同意時，才能拆成多 Agent 任務書；此時每個 Agent 各有一份可獨立貼上的任務書。

把規則分成兩類：

- **硬性限制**：違反即不合格；每條都應來自實測風險、使用者決定、安全要求或權限限制。
- **建議作法**：執行 Agent 可採更好的方式，但須在進度紀錄或最終回報中說明原因與證據。

### 5. 防止取巧、失憶與靜默失敗

依任務風險選用下列機制，不要為極小任務製造多餘檔案：

1. **凍結基準**：記錄測試數、失敗數、略過數、覆蓋率、效能或其他相關指標；完成後不得倒退。
2. **禁止竄改判準**：不得以刪除或略過測試、放寬斷言、模擬被測核心、忽略錯誤碼、造假輸出等方式達標。除非任務本身就是修正測試，否則不得修改驗收標準。
3. **反向驗證**：對警報、驗證器、CI 或防護機制，刻意製造一次安全且可回復的失敗，證明它真的會攔截，再還原測試變更。
4. **斷點續跑**：預期跨工作階段、超過約 30 分鐘或由多 Agent 執行時，在允許寫入的追蹤位置使用 `PROGRESS.md`，記錄已完成事項、證據、下一步與未解風險；接手時先讀取，不要重做。
5. **阻塞回報**：無法安全繼續時，在同一追蹤位置將阻塞原因、已試方法、原始錯誤、受影響範圍及解除條件寫入 `BLOCKED.md`；不得用猜測繞過權限或安全限制。

設定三道止損：

- 任務 0 的前提或基準不符時，停止實作並回報差異。
- 同一驗收連續失敗 3 次時，停止重複嘗試，改查根因或切換方法。
- 結果比基準差時，只還原執行 Agent 本次可明確辨識的變更；不得覆蓋使用者或其他 Agent 的既有修改。無法安全還原時，停止並如實回報。

### 6. 明確劃出授權與多 Agent 邊界

任務書必須列出允許寫入、唯讀與禁止碰觸的路徑或系統。未明確授權時，預設禁止部署、公開發布、推送、合併、寄送、回覆、刪除、付費、修改權限、處理正式資料或永久性操作。

只有使用者同意並行時才拆成多份。每份都加入相同的「全域協作規格」：

- 整體目標、Agent 分工、相依關係與整合順序。
- 各 Agent 不重疊的寫入範圍；共享檔案指定唯一擁有者。
- 跨範圍只讀取與列證據，不直接修改。
- 指定整合負責者與整合後必須重跑的驗收。
- 禁止自行修改 CI、強制推送、改寫歷史或擴大工作範圍。

## 驗收責任

在任務書中提供執行 Agent 看得到的「公開驗收」：可重跑的指令、產物檢查、來源要求及必要的人工驗收步驟。不要強迫所有工作都用指令驗收；介面、文件、研究與外部狀態應採合適的證據類型。

若規劃與執行位於不同會話，可在規劃會話中保留 2–3 個不寫進任務書的獨立抽查點，避免執行 Agent 只針對明示測試最佳化。若使用同一會話，或系統無法保留私有狀態，不得假裝題目仍未洩漏或已保存；待使用者帶回結果時，再依原始需求、實際差異與公開驗收設計新的獨立抽查。

使用者回來要求驗收時，親自重跑可存取的公開驗收與獨立抽查。以 5 行內回報：是否通過、完成內容、關鍵證據、遺留風險、建議下一步。若無法存取執行環境，才提供一段可交給「未參與執行的驗收 Agent」使用的提示詞。

## 交付格式

完成必要提問並取得答案後，最終回覆只包含：

1. 一句使用方式：「在支援 `/goal` 的執行 Agent 輸入 `/goal ` 後貼上以下整段；若工具沒有目標模式，直接貼上整段送出。」再補一句導讀：使用者只需看「這項工作為什麼要做」、「我先代你採用的預設決策」與「完成條件」。
2. 單 Agent 時提供一個包含完整任務書的 Markdown 程式碼區塊。經使用者同意的多 Agent 工作，則依執行順序提供每個 Agent 各一個清楚標示、可獨立複製的程式碼區塊。不要要求另存檔案，也不要替同一份任務書提供第二個啟動指令。
3. 一句收尾：「執行完成後把結果帶回來，我會替你驗收，並用 5 行內說明結果。」

不要在最終交付中附上調查流水帳、推理過程或未整理的筆記。全文不得要求執行 Agent「回來問我」；改用預先定義的預設決策、停止條件與 `BLOCKED.md`。

## 發出前自我檢查

- 任務類型、目標、範圍、權限與完成條件是否一致？
- 所有事實是否標明已實測、使用者決定或暫定假設？
- 寫入範圍是否採允許清單？外部與不可逆操作是否有明確授權？
- 驗收是否涵蓋功能、品質、不退步、防取巧與必要的反向驗證？
- 指令是否已親自驗證；無法驗證的是否放進任務 0？
- 是否包含適量的止損、續跑與阻塞機制，而非機械式加入？
- 是否符合平台長度限制、可一次貼上，且全文使用臺灣繁體中文？
- 多 Agent 任務是否已經使用者同意，且寫入範圍、共享點與整合責任清楚？
