# 教學講義：把一句想法變成 Agent 能獨立跑完的任務書

## 為什麼需要目標任務書

「幫我把測試整理好」、「研究哪個資料庫適合我」、「把這個專案交給幾個 Agent 做」都不是可直接驗收的目標。Agent 收到模糊要求時，通常會自行補完缺少的事實、範圍與成功標準，結果可能出現：

- 用不存在的指令當驗收。
- 為了讓測試通過而略過測試或放寬斷言。
- 修改超出授權的檔案、CI 或正式環境。
- 研究很多資料，卻沒有回答真正的決策問題。
- 工作階段中斷後重做，或不知道從哪裡接手。
- 多個 Agent 同時修改共享檔案，最後無法整合。

`goal-me` 的工作不是直接執行，而是先把模糊想法轉成有證據、有邊界、能停止、能續跑、能驗收的工作規格。

## 你會學到什麼

完成本週練習後，你會懂得：

1. 把「想要的成果」與「以為可行的手段」分開。
2. 判斷執行型、探索型與混合型任務。
3. 用事實來源與權限邊界減少 Agent 幻覺與越權。
4. 寫出不鼓勵刪測試、跳過錯誤或造假輸出的完成條件。
5. 為長任務設計止損、進度紀錄與阻塞回報。
6. 在多 Agent 工作中指定唯一擁有者與整合順序。

## 核心觀念

### 1. 三個角色不要混在一起

- **決策者**：提出想法、決定取捨與授權高風險操作。
- **規劃與驗收 Agent**：查證現況、補齊規格、保留獨立抽查並驗收結果。
- **執行 Agent**：依任務書在允許範圍內工作，遇到停止條件就留下證據。

讓執行 Agent 自己寫考題又自己批改，容易只針對明示條件最佳化。規劃與驗收最好使用不同會話；若只能使用同一會話，等看到實際差異後再設計新的抽查。

### 2. 先查證，再提問

可以從工作區找到的內容，不需要詢問使用者。例如套件指令、測試名稱、檔案路徑、目前分支與基準數字，都應先實際檢查。

只有答案會改變範圍、驗收、風險、成本或排程，而且無法自行查證時才提問。問題要一次問完、最多 5 題，每題提供互斥選項、影響與建議。

### 3. 每項重要資訊都要有身分

- `已實測`：本次真的執行或直接讀取得到。
- `使用者決定`：使用者明確選擇。
- `暫定假設`：目前無法查證，附驗證方式與不成立時的處理。

舊 README、過去報告或別人的說法只能當線索，不能自動升級成目前事實。

### 4. 任務型態會改變驗收方法

**執行型**會產生修改或成品，適合用測試、建置、產物、畫面與人工操作驗收。

**探索型**要回答研究或選型問題，適合用來源品質、比較準則、反證、信心程度與決策可用性驗收。硬塞測試數量只會得到為了湊數的報告。

**混合型**先研究再實作。任務書必須設定進入實作的門檻；門檻未達就停在研究結果，不要為了看起來完成而硬做。

### 5. 權限邊界要寫成允許清單

任務書至少要分成：

- 允許寫入。
- 唯讀取證。
- 禁止操作。

未取得使用者明確授權時，不應部署、公開發布、推送、合併、寄送、回覆、刪除、付費、改權限或處理正式資料。

### 6. 驗收要防止最省力的錯誤解法

如果目標只寫「讓測試變綠」，Agent 最省力的路可能是刪除測試、加入 skip、放寬斷言、模擬被測核心或忽略錯誤碼。任務書必須凍結基準，禁止竄改判準，並在適合的地方加入反向驗證。

反向驗證的問題是：「這裡真的壞掉時，誰會知道？」如果答案是沒有人，就要安全地製造一次失敗，證明警報、CI 或驗證器會攔截，再還原測試變更。

### 7. 長任務要能停止與續跑

長任務使用 `PROGRESS.md` 記錄完成內容、證據、下一步與風險；無法安全繼續時使用 `BLOCKED.md` 記錄原始錯誤、已試方法與解除條件。

三道基本止損：

1. 任務 0 的前提或基準不符時停止實作。
2. 同一驗收連續失敗 3 次時停止重複嘗試，改查根因。
3. 結果比基準差時，只還原本次可辨識的變更，不覆蓋其他人的工作。

## 動手做

### 步驟一：安裝並確認技能結構

依 README 將 `completed/goal-me` 複製到個人技能目錄。確認以下檔案存在：

```text
goal-me/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── references/
    └── anatomy.md
```

重新啟動 Agent 工具後，用 `$goal-me` 或 `/goal-me` 明確呼叫一次。

### 步驟二：先做執行型任務

在一個可安全練習的專案輸入：

```text
使用 goal-me，幫我把「讓 Agent 把這個專案的測試流程整理好」轉成可獨立完成的目標任務書。先查工作區，再決定是否需要問我。
```

觀察 Agent 是否先檢查 `AGENTS.md`、套件腳本、測試與 CI。若它詢問可以自行查到的問題，要求它回到調查階段。

### 步驟三：回答關鍵問題

Agent 最多只能一次詢問 5 題。回答前先看每個選項會改變什麼，不要只選看起來最快的選項。

不可逆操作、正式環境、付費或外部傳送不能用預設值代替授權。若不想真的執行，可明確選擇「只完成任務 0 與計畫，不修改檔案」。

### 步驟四：檢查六節任務書

任務書應包含：

1. 這項工作為什麼要做。
2. 已知現況與證據。
3. 範圍、授權與預設決策。
4. 執行任務與順序。
5. 執行控制與回復。
6. 完成條件與回報格式。

先看第 1、3、6 節即可快速判斷方向是否正確，再檢查中間三節的證據與執行細節。

### 步驟五：用新的執行 Agent 跑任務

支援 `/goal` 的工具依輸出說明貼入目標模式；沒有目標模式時，直接把整份任務書貼到新的對話。

新的會話可以降低獨立抽查洩漏，也可以驗證任務書是否真的不依賴規劃時的對話內容。

### 步驟六：帶回結果驗收

把執行 Agent 的變更、測試輸出、產物與遺留風險交回規劃 Agent。驗收報告應在 5 行內說明：

1. 是否通過。
2. 完成了什麼。
3. 關鍵證據。
4. 遺留風險。
5. 建議下一步。

### 步驟七：再做探索型任務

輸入：

```text
使用 goal-me，幫我寫一份讓 Agent 研究「這個專案是否需要加入 Redis」的目標任務書。先把「降低延遲」和「一定要用 Redis」分開。
```

檢查輸出是否先定義決策問題與比較準則，再要求來源、反證、成本、信心程度與下一個低成本驗證，而不是直接開始安裝 Redis。

## 本週任務

1. 完成一份執行型目標任務書。
2. 完成一份探索型目標任務書。
3. 比較兩份任務書的完成條件有何不同。
4. 選一份交給新的 Agent 或新會話，只執行到安全範圍。
5. 帶回結果完成一次獨立驗收。

## 成果證據

- 技能成功觸發的截圖。
- 一句話原始需求與單輪問題。
- 執行型與探索型任務書各一份。
- 至少一份實際執行或只讀預檢結果。
- 5 行內驗收報告。

分享前移除個資、客戶資料、內部網址、API Key、絕對路徑與未公開程式碼。

## 通過標準

- [ ] 兩份任務書都回答原始需求，沒有把指定手段誤當目標。
- [ ] 所有重要資訊都有事實來源或驗證方法。
- [ ] 執行型使用可重跑指令、產物或人工操作驗收。
- [ ] 探索型使用一致的比較準則、來源、反證與信心程度驗收。
- [ ] 權限邊界與不可逆操作授權清楚。
- [ ] 完成條件能阻止刪測試、忽略錯誤或造假輸出等取巧方式。
- [ ] 執行失敗時能從 `PROGRESS.md`、`BLOCKED.md` 或最終回報接續。

## 失敗時的最短重試路徑

1. 先用明確名稱重新呼叫技能。
2. 確認 `SKILL.md` 與 `references/anatomy.md` 沒有分開。
3. 將需求縮成一個 Agent、一次貼上可以完成的範圍。
4. 把無法實測的指令與數字移到任務 0。
5. 將所有外部或不可逆操作改為禁止，先完成只讀預檢。
6. 重新產生任務書並只檢查第 1、3、6 節，再進入完整驗收。

## 延伸思考

- 哪些任務其實不需要 `PROGRESS.md`？
- 哪些驗收一定要由不同 Agent 執行？
- 多 Agent 同時修改 lockfile、schema 或 CI 時，應由誰擁有共享寫入點？
- 如果研究結果否定使用者原本指定的工具，任務書應如何停止而不是硬做？
